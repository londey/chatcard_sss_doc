# Design and construction constraints

## Security Architecture Constraints

**CONS-SEC-001**: The system architecture shall be designed to support evaluation against the following Common Criteria Protection Profiles (as referenced in Section 2):

- IoT Secure Communications Module Protection Profile
- PP-Module for Bluetooth
- Cryptographic Service Provider Protection Profile
- IoT Secure Element Protection Profile (if applicable)

**CONS-SEC-002**: Cryptographic implementations shall use algorithms and key sizes approved for the target security level, following guidance from the Cryptographic Service Provider Protection Profile.

**CONS-SEC-003**: The Bluetooth LE implementation shall comply with security requirements specified in the PP-Module for Bluetooth, including proper key generation and secure pairing protocols.

## Hardware Design Constraints

**CONS-HW-001**: If a dedicated secure element or cryptographic coprocessor is used, it should be selected from devices that have achieved or can achieve Common Criteria certification under the IoT Secure Element Protection Profile.

**CONS-HW-002**: The hardware design shall support secure key storage with protection against:

- Physical tampering
- Side-channel attacks (power analysis, timing analysis)
- Fault injection attacks

**CONS-HW-003**: The device shall be designed to support secure boot and firmware verification processes.

## Software Design Constraints

**CONS-SW-001**: Security-critical code (cryptographic operations, key management) shall be isolated from non-security-critical functions.

**CONS-SW-002**: The software architecture shall minimize the Trusted Computing Base (TCB) to reduce the attack surface.

**CONS-SW-003**: All external interfaces (Bluetooth LE, user input, display output) shall include appropriate security validation and sanitization.

## Development and Testing Constraints

**CONS-DEV-001**: Development processes shall follow secure coding practices appropriate for security-critical embedded systems.

**CONS-DEV-002**: The design shall support security testing methodologies including:

- Penetration testing
- Cryptographic algorithm verification
- Side-channel analysis
- Fuzzing of communication protocols

**CONS-DEV-003**: Documentation shall be maintained to support potential Common Criteria evaluation, including:

- Security architecture documentation
- Threat model and risk analysis
- Cryptographic key management procedures
- Secure development lifecycle evidence
